# 混乱用户导航验收

## 范围

EGO `taskSpace(8).page('p3')`，开发页面 `http://127.0.0.1:7001/`；页面内使用 3 个合成分组、每组 3 个子分组、每子组 12 条书签。页面无 `window.utools`，不代表真实宿主或持久化验证。并行开发触发热更新和页面重载，以下结果对应操作时的代码，最新集成版本仍需复验。没有采集稳定的导航性能计时。

## 已观察结果

| 场景 | 实际结果 |
| --- | --- |
| 快速依次点击组 1、组 2、组 0 | store 活动组、顶栏高亮和内容面板均为组 0。 |
| 组 0 点击第 3 子分组，切到组 1 再切回 | store 和侧栏恢复第 3 子分组，滚动位置均为 828.5px。 |
| 双击当前分组 | 修复前回到顶部，但侧栏仍高亮第 3 子分组；修复后顶部为 0，侧栏和 store 均为第 1 子分组。 |
| 切组后滚动 | 在组 1 从底部向上滚至 201px，侧栏高亮第 1 子分组。 |
| 搜索并按 Esc 退出，随后滚动 | 搜索词清空，回到组 1；滚至 729px 时高亮第 2 子分组。 |

双击回顶修复在 `src/views/home/useHomeGroupNavigation.ts`；滚动监听切组和搜索退出后的重新绑定由主代理修改 `src/views/home/useHomeScrollSpy.ts`。修复后的上述浏览器结果不等于对最新整合代码的完整验收。

## 最新键盘修复与源码复核

- first-user 在 p7 实测：焦点位于侧栏菜单“重命名”时按 Enter，打开了选中书签，菜单未执行。修复后 p3 小数据实测：聚焦子分组更多按钮按 Enter 打开菜单，再聚焦“重命名”按 Enter，出现原名称的内联输入框，菜单关闭，未打开外链。普通按钮、书签卡片和搜索框 Enter 仍需最终版本复验。
- 对最新导航代码复核：切组前校验组，按组恢复子分组并同步 store；切组与段落定位复用可取消的滚动计时器，延迟回调检查目标组。以上是源码结论，快速连续切换、搜索与定位交错及虚拟列表极端数据仍需在最终集成版本重复验收。
- ☑ 已记忆子分组被删除后切回：p3 先把组 0 第 3 段记为 828.5px，切到组 1，再通过真实 store 删除组 0 第 3 段。修复前切回时回退第 1 段但位置被裁到 228px；修复后组 1 保持 0px，切回组 0 后位置为 0px，侧栏和 store 均为有效的第 1 段。启动时连续恢复记录指向已删除子分组的独立边界仍未实测。
- 最新 p3 复验使用 2 组、每组 3 段、每段 12 条合成书签：搜索“混乱0-1”出现对应结果，Esc 清空搜索回组 0；点击第 3 段至 828.5px，再实际滚轮向上 450px 至 378.5px，侧栏高亮第 2 段。
- 最新 p3 拖拽 Esc：通过浏览器鼠标输入按下并移动书签 `chaos-b0-0-9`，看到拖拽预览与源卡片 opacity 0.4；按 Esc、释放鼠标后预览消失、源卡片恢复，所属 12 条书签 ID 顺序未改变。之前鼠标动作未成功起拖的尝试不作为通过证据。

## 未完成与风险

- 拖拽跨段、拖拽过程中切组及触摸拖拽尚未覆盖；早期误触产生的 p10、p11、p12 外链页已由主代理关闭。
- 最新持久化合并的浏览器回归：无 uTools 的 p3 中，组 0 点击第 3 子分组得到滚动位置 828.5px，切组 1 并等待超过 400ms 后切回，实际位置为 0、高亮第 1 子分组。复现时写入不可用，刷新从空存储读取并覆盖内存 map；调整合并保留内存 map 后重复相同操作，切回仍为 828.5px、第 3 子分组。随后双击当前组，实测位置 0，侧栏和 store 均为第 1 子分组。
- ☑ 两页面交错保存：p3 和 p17 同源页面在运行时替换真实 `utoolsStorage` 的面板读写适配器，以共享的独立 localStorage 键模拟宿主存储；各页面使用真实 `useHomePanelPersistence` 和 2 组小数据。按组 0 第 2 段、组 1 第 3 段、组 0 第 3 段、组 1 第 2 段、组 0 第 2 段交错操作并等待落盘，最终共享 map 同时保留两组各自的 613px 和第 2 段。模拟键已清除，页面已重载；这不是实际 uTools 多窗口验证。
- ☑ 写入失败后下一次 flush 重试：p3、p17 运行真实持久化 hook，面板存储适配器改接共享 localStorage mock。p3 的 mock 保持返回 `false`，组 0 滚至 828.5px，并通过模拟 `beforeunload` 触发真实退出保存，观察失败写入携带 829px 和第 3 子组；p17 成功保存组 1 的 613px、第 2 子组。随后将 p3 mock 恢复为返回 `true`，再次触发退出 flush，最终 map 同时保留组 0 的 829px、第 3 子组和组 1 的 613px、第 2 子组。失败期间发生多次由正常操作或生命周期触发的写入尝试；此结果验证下一次 flush 重试，不代表后台无限自动重试。mock 键已清除，页面已重载；真实 uTools 失败恢复仍未实测。
- 数据量较大时的导航耗时、真实 uTools 退出和重启恢复、不同窗口并发操作、拖拽跨段及虚拟列表边界未覆盖。主代理负责独立性能采样。
- 最终导航修改后 `bun run type-check`、`bun run build` 均通过；最终集成仍需整体验收。
